# V2.3 AI 原生开发治理：让 Codex 精确开发而不是盲目改代码

## 1. 工程目标和可测指标
- **变更定位**：每次任务引用对应的 `module_id`、模块地图和真实代码路径；禁止整仓无依据扫改。
- **变更审计**：每张 PR 描述需求、影响范围、兼容性、数据库/Prompt/模型影响、风险与测试证据。
- **修复可信**：Bug 必须先有可复现证据或明确的非确定性故障证据，不能将猜测写成根因。
- **持续创作可靠**：调度成功率、审核通过率、镜头渲染成功率、任务重复率、人工发布包交付成功率独立监测。
- **业务红线**：AI 不调用社媒最终发布操作；人工发布不等于保证平台合规或免处罚。

## 2. AI 开发任务卡必须包含
`issue_id, product_goal, affected_domains, observed_behavior, expected_behavior, acceptance_tests, forbidden_changes, risk_level, migration_needed, version_fields, estimated_cost, human_approval_needed`。
- 功能需求先列正向用例和负向用例。涉及“创作者停用”“人工发布”“内容真实性”必须有硬性安全用例。
- Bug 需要系统版本、环境、任务 ID、时间、最小复现路径、输入摘要、日志链接、预期/实际差异。不可要求用户上传密码和 Cookie。
- Codex 如果无法定位真实根因，应先补观测数据/复现机制；**不能为了提交代码而猜改**。

## 3. 项目文档“唯一真相源”
1. `AGENTS.md` AI 工作总规约；
2. `docs/01_产品完整开发方案_人工发布版.md` 产品边界与核心流程；
3. `docs/architecture/MODULE_MAP.md` 组件责任；
4. `docs/architecture/CONTRACTS.md` 关键类型与接口；
5. `docs/adr/` 架构决策（新增前征询/审批）；
6. `PROJECT_STATUS.md` 实际开发进度与证据；
7. `CHANGELOG.md` 用户能感知的变更；
8. `VERSION_MANIFEST.example.json` 发行版本冻结清单；
9. `docs/09_版本发布回滚维护.md` 发布和回滚操作。
若源码与文档冲突：不能擅自认定其中一个正确。先验证真实生产行为、历史变更和测试，决定是修源码、修文档还是修产品契约。

## 4. 强制小步开发规则
- 正常改动尽量限单模块或单接口边界；涉及跨模块变更，先输出调用链与影响矩阵。
- 复杂功能先实现最短真实闭环：日程→内容→视频/图文→审核→导出包→用户登记→数据回流。
- 每个关键接口先定义 DTO/schema、错误码与鉴权，再开发实现；客户端消费版本化 API。
- 不跨层调用数据库，不共享未经审核的原始模型输出作为后续已验证事实。
- 任何内容事实变更、素材版本变更都应使依赖内容重新检查；视频镜头有单独的 `shot_revision`。
- Prompt、工具契约、模型版本同时变更时，必须做兼容矩阵测试，否则拒绝发布。
- 业务输出的“成功”必须有实际产物或真实持久化回执，不允许用 HTTP 200 包裹下游失败。

## 5. 多 AI 协作：最多三种角色，不能无限扩张
- **Architect/Planner**：只负责需求边界、变更范围、架构决策、验收列表；不修改生产数据库。
- **Implementer**：按已批准范围修改文件和测试，避免顺手重构。
- **Reviewer/Verifier**：独立检查错误处理、回归、安全、许可和实际测试日志，明确阻断项。
如果只有一个 Codex 运行，也应依次执行三种步骤并保持可检查的报告。审查结果**不是 AI 自评“高分”就放行**；关键 CI/人工审批必须实际通过。

## 6. 开发分支与提交约定
- 使用 `feat/<issue>-<slug>`, `fix/<issue>-<slug>`, `docs/<issue>-<slug>`, `hotfix/<issue>-<slug>`；长期主分支 `main`；按需要维护 `release/x.y`。
- 提交信息采用 `feat(video): ...`, `fix(creator): ...`, `test(handoff): ...` 等 Conventional Commits 风格，正文写因果而非只写“fix”。
- 所有生产变更走 PR 和受保护分支；至少代码审查、CI、许可证审计、安全扫描和冒烟测试。对于用户自行部署的单人开发，仍避免直接推送未经测试的线上环境。
- **禁止**提交 API Key、私信凭据、个人信息、原始非授权测试资产、模型权重到 Git。

## 7. 每次 PR 的可验证交付
| 证据 | 必须内容 |
|---|---|
| 需求 | Issue 编号、用户价值、明确验收 |
| 改动 | 影响模块、文件、数据库、Schema |
| Bug 根因 | 证据、复现用例、首次失败 span |
| 兼容 | 前端/API/DB/Worker/Prompt/模型/模板版本矩阵 |
| 测试 | 实际命令、Exit code、日志/产物路径 |
| 安全 | 人工发布禁令、数据权限、提示词注入与版权 |
| 运行 | 错误码、可观测性、失败降级和费用 |
| 变更说明 | 文档、CHANGELOG、状态台账、回滚计划 |

## 8. 模块归属与变更影响规则
改动 `VideoProjectIR` → 回归镜头编辑、缓存键、导入导出、所有 Provider；改动 `creator_schedules` → 回归暂停/恢复、时区、重复触发、重启恢复；改动 `prompt/strategy` → 回归事实准确性、选题多样性、预算和许可证；改动 `handoff` → 保证从不出现第三方写操作。跨模块修改必须提供变更影响表。

## 9. 智能诊断 ≠ 自动修复生产
允许 AI 从**脱敏**的追踪、指标和错误记录提出候选根因及建议，提供证据链接和置信度。不得自行对生产环境执行 SQL、重发视频、改预算、修改凭据、重新授权或更新版本。线上修复走维护审批与变更流程。

## 10. M0 必须完成的工程基线
建立仓库模块地图、状态台账、API 错误码、任务回执 Schema、版本矩阵、最小日志关联示例、CI 入门门禁、恢复手册和第一条端到端回归样例。**先让工作流能定位并复现错误，再接入更多视频模型。**
