# V2.3 故障定位与可观测性设计

## 1. 最小故障定位目标
用户报告“今天的宣传视频没出来”时，系统应快速找到：具体 `creator_run` → 内容 → 镜头 → 生成器/渲染 Worker → 首个失败 span → 实际可验证错误 → 当时版本 → 可重试范围。

**目标并非保证每个 Bug 自动精准找到根因**。外部模型随机性、第三方系统不可观测和并发竞争会造成证据不足；AI 应明确输出“证据不足、需补采集”，不能假装确定。

## 2. 推荐技术分层
- OpenTelemetry：Trace / Metrics / 关联日志；HTTP、任务队列、Worker 用 W3C `traceparent` 传播。建议使用 SDK 自动插桩并添加业务标签。
- Langfuse（可选、自托管或托管）：Prompt 版本、模型调用、token 与评测；**不要默认把用户素材/对话原文发送到第三方**。
- Prometheus + Grafana（可选）：应用层指标、队列积压、GPU/CPU、视频质量、费用；报警按可操作性设置。
- Sentry（可选）：前后端异常聚合；适合定位 JS/框架错误，但不能替代业务追踪。
- 对象存储：镜头预览/失败片段/技术元数据；保留期和权限需单独控制。

## 3. 强制业务字段
```
trace_id request_id creator_run_id content_id video_project_id
shot_id shot_revision render_job_id provider provider_request_id
error_code stage status duration_ms retry_count git_sha release_id
prompt_version model_id model_revision template_version ir_schema_version
asset_manifest_sha256 tenant_id_hash  resource_class  billing_reservation_id
```
字段不存在应写 null；**严禁**在日志中保存明文密码、Cookie、用户私人文档原文、原始 Prompt、授权 Token、敏感文件路径和平台私信内容。用户身份在公共监测中做去标识化，采样、保留和导出均遵守最小化原则。

## 4. 故障链举例（虚构演示）
```text
creator_run_id=run_demo_001
trace_id=0123456789abcdef0123456789abcdef
  creator.daily_plan         OK
  content.script             OK
  video.storyboard           OK
  shot.render (shot_03)      ERROR VID_RENDER_RESOURCE_EXHAUSTED
    provider=wan_worker
    evidence: gpu_memory_free_mb=0, provider_error=CUDA out of memory
  video.compose             SKIPPED_DEPENDENCY
```
结论应写：“**观察到**第 3 镜头的提供者返回 OOM；**推测**显存不足与模型并发或分辨率有关；建议检查 GPU 使用率并单镜头低清复现。”
不得写“100% 确定是并发导致”或直接替换用户指定的视觉风格。

## 5. 统一错误码设计
- `CREATOR_SCHEDULE_*` 调度（重复、过期、暂停、时区失效）
- `AGENT_PLAN_*` 策划（超时、无可验证事实、工具不可用）
- `ASSET_*` 素材（缺失、无许可、版本过期、哈希不符）
- `VID_*` 视频（Provider 不可用、GPU 资源耗尽、渲染超时、合成失败、结果哈希失败）
- `QA_*` 质量（技术黑帧、字幕越界、版权不明）
- `COMPLIANCE_*` 合规（阻断、待人工）
- `HANDOFF_*` 发布包（导出失败、已过期、人工登记）
- `METRICS_*` 数据（来源不可信、格式错误、时窗不可比）
- `BUDGET_*` 成本（额度不足、重复扣账风险）
详见 `engineering/contracts/error_codes.json`。

## 6. 告警与故障级别
| 级别 | 示例 | 处理要求 |
|---|---|---|
| P0 | 跨租户数据泄露；出现非用户触发的平台发布请求；费用无限增长 | 立即暂停对应功能/相关任务，安全与权限调查 |
| P1 | 多用户持续任务失效；普遍渲染失败；长时间未交付内容 | 当班响应，保留证据，回退最近变更 |
| P2 | 单任务失败、个别 Provider 不可用 | 单任务重试/兼容引擎建议与人工告知 |
| P3 | 低影响 UI 缺陷、说明不一致 | 按迭代排期修复 |

每条告警带责任域、代码版本、链接与处置动作；别用大量无用警报淹没开发者。

## 7. 故障诊断操作步骤
1. 确定 `creator_run_id` 和用户报错时间；获取用户授权的脱敏诊断包。
2. 查询失败 trace 和首次错误 span，核实前置步骤是否成功；不要只看 UI 最后一条 error。
3. 读取错误码和实际 Provider 错误，检查重试记录、资源指标和预算账本。
4. 查询 `release manifest`：代码 SHA / prompt / 模型 / 模板 / IR / migration。
5. 执行**最小可复现用例**，条件包含相同资产哈希、Provider/模型版本、输出比例、分辨率、seed（如有）、并发设置；无法完全复现时报告差别。
6. 提出 1–3 个根因候选，标记证据和置信度；修复后补单元/集成/回归/压力/故障注入测试。
7. 故障修复 PR 交付前后对比。生产修复必须有审批与回滚条件。

## 8. 三大关键“不能自动重复执行”场景
- 平台最终发布：压根不存在自动发布操作；用户在官方平台手动执行。
- 视频生成收费请求：Provider 回执未知时先查询请求状态、费用，再判断是否重试；不可无条件再次生成并重复扣账。
- 数据库迁移：失败后不要把 up migration 简单反跑，当存在不可逆操作时使用前向修复/备份恢复。

## 9. 可视化诊断中心设计
管理后台增加 `/ops/diagnostics`：按任务 ID/日期/错误码/引擎过滤；展示阶段树、失败镜头、相关版本、建议处理、审核记录、脱敏诊断导出。普通用户仅看到“错误阶段+可操作建议”，管理员才看基础设施指标；敏感字段必须按角色过滤。

## 10. 观测与隐私
保留策略可配置（示例：普通 traces 7–14 天、错误 traces 30 天、已授权的产物元数据随项目，真实日志视法规/业务要求），不能把这些数字当作普适法律要求。生产原文数据默认不传给第三方监控系统；提供用户自助删除/诊断包导出。开发示例只使用合成数据。
