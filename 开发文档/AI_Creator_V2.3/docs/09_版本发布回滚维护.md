# V2.3 版本、发布、回滚与长期维护规范

## 1. 版本必须分层
| 版本项 | 样例 | 规则 |
|---|---|---|
| 应用版本 | `2.3.0` | SemVer：破坏兼容升级 major、兼容功能 minor、修复 patch；方案版本不等于软件上线版本 |
| Git 修订 | `git_sha` | 构建后不可变，服务启动可追溯 |
| 数据库 schema | `20261105_001` | 通过显式 migration 演进，不允许线上随意 AutoMigrate |
| REST API | `/api/v1` | 破坏性接口新增 v2 或兼容适配 |
| 视频工程 IR | `1.0` | 旧工程有迁移器与 golden fixture |
| Agent 图 | `creator_graph@1.2` | 旧运行任务按旧版本恢复，避免状态解包失败 |
| Prompt | `creator_prompt@17` | 模型与工具变化需记录，与追踪绑定 |
| Model Provider | `wan_adapter@2.1` | 记录依赖模型、实际权重版本和设备需求 |
| 镜头/模板 | `intro_mg@3.4` | 模板升级不自动篡改已发布工程 |
| 数据与学习策略 | `strategy@5` | 仅按证据提案并保留回滚版本 |

**版本冻结不是把所有组件强制同步大版本**。每次发布生成 `release_manifest.json`，把已部署版本绑定到一个不可变发行编号。

## 2. 分支与发行节奏
- `main`：始终可构建，保护合并；`feat/*` / `fix/*` 小任务；`release/x.y` 在需要长期维护时建立；生产紧急修复走 `hotfix/*`。
- 方案/文档版本 `V2.3` 与实际软件 SemVer 分开：目前交付的是**规范包，不是已发行 2.3.0 软件**。
- 每周可做小版本发布、月度稳定版，频率按人手与用户反馈决定；重要安全修复可走例外流程但仍保留记录。

## 3. 发布流水线（带手工审批）
`PR → lint/typecheck/单元 → 契约/API → Agent 评测 → 视频 golden → E2E 人工发布 → License/SBOM/secret scan → staging → smoke → 版本冻结 → 人工批准生产灰度 → 监测 → 扩容/回滚`。
- 视频 golden 用 3 类稳定成片：真实录屏、MG、素材混剪；后续增加 AI 视频 Provider 标记为非确定性，只测可验证技术指标与结构约束。
- 模型/Prompt 变更不应因为“不改代码”而绕过评测；一旦部署标签变化，保留对应版本和回归报告。
- 部署灰度基于工作区/任务标志，**不要**将运行中的长任务无条件切到新 Worker。
- 数据库先做非破坏性的 expand，再逐步迁移使用者，最后 contract；回滚应用时确保旧版本仍能读取扩展 schema。
- 如果采用 Temporal，优先按官方 Worker Versioning 保证长工作流部署兼容；无此能力时须测试 patch/replay。若采用 PostgreSQL + Celery，也必须在任务消息里固定 handler/schema 版本并定义旧任务兼容期。

## 4. 发布前清单（任何一项不满足不得把版本标记“stable”）
- [ ] `PROJECT_STATUS` 证据真实、无虚假完成项
- [ ] 业务不可变红线自动化/人工检查通过
- [ ] 迁移有真实演练和备份恢复路径
- [ ] OpenAPI/IR/Prompt/模型/Provider 兼容矩阵与锁版本完整
- [ ] 样例长任务的恢复、暂停、取消、幂等通过
- [ ] 视频渲染有效 MP4，ffprobe 元数据正确，逐镜头缓存有效
- [ ] 导出包存在真实文件，用户手动发布登记状态正确
- [ ] 安全扫描、许可证与素材来源审计通过
- [ ] 部署包/镜像有 SHA256 与 release manifest
- [ ] 主责人批准发布且定义回滚触发阈值

## 5. 回滚是多维的，不只是 `git revert`
| 出错维度 | 推荐回滚 |
|---|---|
| Web/API | 回切上个镜像/标签与配置 |
| 长任务 Worker | 保留旧任务处理器和版本路由，运行中的 Workflow 按原版本结束 |
| Prompt | 标签恢复到上个稳定 Prompt 版本并留审计 |
| 模型 | 回退兼容 provider 与权重版本；记录已有输出不可自动变更 |
| 视频模板 | 使用上个模板版本；已完成视频工程仍指向旧版 |
| 数据库 | 优先扩展兼容/前向修复；数据损坏按演练过的备份+PITR 恢复 |
| 对象存储 | 不可变资产 + 版本指针；回退指针而非直接覆盖素材 |
| 自动运营策略 | 将 `strategy_version` 指回上次用户确认的稳定版本 |

回滚**不能**撤销用户已经亲自在第三方平台发布的帖子；只能在本产品中暂停后续内容/通知用户修改或删除其平台内容。记录生产回滚时间、影响租户和未完成任务。

## 6. 数据库、素材与灾难恢复
- 日备份 + 恢复演练、独立权限与加密；PostgreSQL 用 PITR 时需要 WAL 存档并周期性验证恢复点。
- 用户视频工程、版本快照与原始资产按生命周期管理：存储成本阈值、冷存储、留存与删除权限。
- Prompt/Agent 日志与业务内容存储分开，遵守数据最小化；避免在监测 SaaS 中泄露个人简历、账号资料或私有软件源代码。
- 从用户备份恢复后重新核对账本、任务幂等键、导出包链接和暂停状态，防止重复生成/计费。

## 7. 持续维护制度
| 周期 | 内容 |
|---|---|
| 每天 | 创作队列、失败率、预算与异常告警；待用户处理的失败列表 |
| 每周 | 依赖安全补丁、性能回归、内容质量失败样本、PR 清理 |
| 每月 | 模型/Provider 兼容检查、成本基线、备份恢复抽检、文档和手册同步 |
| 每季度 | 安全审计、许可证/素材/模型权重盘点、灾难恢复演练、旧版本淘汰计划 |

**依赖升级**：Renovate/Dependabot 只负责提出 PR；大版本/数据库/生成模型/核心渲染链必须人工审核，禁止自动合并到生产。Renovate 的 `AGPL-3.0-only` 属于工具本身许可证，采用云端 App 不代表产品自动被重新许可，但若将其源码作为产品组件整合应独立审查。

## 8. 版本异常追溯
每次线上故障都展示 `release_id`, `git_sha`, `db_schema_version`, `video_ir_version`, `prompt_version`, `provider_adapter_version`, `model_revision`。对账时按单个 `creator_run_id` 找到实际使用的版本（不能只读取“当前线上最新版”，因为长任务可能始于旧版本）。
